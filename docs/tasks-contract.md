# Задачи и категории: проект требований MVP

**Статус:** первый срез создания и списка согласован, следующие срезы описаны как план. Полный full-stack функционал ещё не реализован; этот документ не подтверждает наличие endpoint или схемы БД. Auth-контракт находится в [auth-contract.md](auth-contract.md).

Уточнение границ: **Tasks** и **Categories** — отдельные фичи. Ниже описано также их будущее взаимодействие; требования категорий и их интеграции не входят в готовность Tasks. Сначала Tasks работает без выбора, отображения и фильтрации категорий; эти возможности добавляются вместе с Categories.

Реализованы Domain-сущность `TodoTask`, `TaskPriority`, нормализация/валидация и unit-тесты создания. В Application добавлены `CreateTaskCommand`/`CreateTaskHandler`, `GetTasksQuery`/`GetTasksHandler`, модели результатов, `ITaskRepository`, перевод ожидаемых ошибок фабрики и unit-тесты обработчиков. В Infrastructure добавлены `TaskRepository`, `TodoTaskConfiguration`, `AppDbContext.Tasks`, миграция `AddTodoTasks` и SQL-скрипт. 2026-10-21 миграция применена к локальным TodoAppDev/TodoAppTest; 14 repository SQL-кейсов прошли. Добавлены DI wiring, HTTP DTO и защищённые POST/GET `/api/tasks`, HTTP/DI-тесты и 3 полных HTTP → SQL Server сценария. Подробности — [tasks-http-contract.md](tasks-http-contract.md) и [tasks-persistence.md](tasks-persistence.md). Angular получил защищённый lazy `/tasks`, навигацию, чтение первой страницы и обработку Tasks `401`. Creation and URL-driven server pagination UI are implemented; live acceptance of the new pagination remains a separate check. See [pagination behavior](tasks-pagination-frontend.md). См. [tasks-frontend.md](tasks-frontend.md). Категории, изменение состояния/редактирование остаются следующими срезами.

## 1. Цель и границы

Авторизованный пользователь ведёт личный список дел: создаёт задачи, просматривает и редактирует их, отмечает выполнение, возвращает к работе, удаляет, распределяет по собственным категориям и находит нужные задачи через поиск/фильтры/пагинацию.

Приоритет и описание — небольшие дополнения к исходному тестовому. Нет совместных списков, исполнителей, дедлайнов, напоминаний, файлов, подзадач, повторений, корзины или истории изменений. Нет real-time синхронизации вкладок и пользовательских вариантов сортировки. Квоту количества задач на аккаунт пока не вводим.

## 2. Данные задачи

| Поле | Правило |
| --- | --- |
| Идентификатор | Назначается сервером, неизменяемый |
| Владелец | Текущий авторизованный пользователь; клиент не выбирает/не меняет владельца |
| Название | Обязательно; 1–200 Unicode code points после удаления whitespace по краям; одна строка |
| Описание | Необязательно; до 2000 Unicode code points после удаления whitespace по краям; пустое/whitespace-only значение означает отсутствие описания |
| Приоритет | Только Low, Normal, High; при создании по умолчанию Normal |
| Состояние | Active или Completed; при создании Active |
| Категория | Необязательная; не более одной, только собственная категория пользователя |
| Создана | Время сервера в UTC; клиент не задаёт/не изменяет |
| Завершена | Время сервера в UTC либо отсутствие значения, если Active |

Unicode code point здесь означает ту же единицу подсчёта, что в текущем password-контракте: например, один emoji может занимать несколько UTF-16 code units. Конкретную вместимость SQL-колонок согласовать с этими границами при EF mapping, а не механически приравнивать к ним размер nvarchar.

Для текста допускаются Unicode и emoji. Внутренние пробелы сохраняются. Название не допускает управляющие символы; описание допускает переводы строк и табуляцию, но не остальные управляющие символы Unicode категории Cc. Введённый текст отображается как обычный текст: HTML/Markdown не исполняются и не интерпретируются. Одинаковые названия задач разрешены, включая задачи одного пользователя.

Текст должен состоять из корректных Unicode scalar values: некорректные UTF-16 последовательности отклоняются, а не заменяются автоматически. Ограничения символов проверяются после Trim; внутренние Unicode line/paragraph separators также запрещены в однострочном названии. Один визуальный символ может состоять из нескольких code points: например, `e` + combining accent считаются двумя.

## 3. Создание

- Пользователь открывает форму, вводит название; описание, приоритет и категория доступны как дополнительные поля.
- Минимально достаточно одного валидного названия.
- Созданная задача имеет серверные ID/owner/time, состояние Active и не имеет времени завершения.
- Успех подтверждается только ответом API; отмена формы не создаёт задачу.
- После успеха пользователь возвращается к списку. Поиск/фильтры сбрасываются к значениям по умолчанию, открывается первая страница: новая задача видна в общем списке.
- Повторные клики во время отправки не создают дополнительные клиентские запросы. Это не обещание exactly-once при сетевых сбоях.

## 4. Просмотр и редактирование

- Список показывает название, приоритет, состояние, категорию либо «Без категории» и дату создания.
- Полное описание доступно в представлении/форме конкретной задачи; необязательно помещать весь текст в строку списка.
- Пользователь редактирует название, описание, приоритет и категорию. Правила полей те же, что при создании.
- Категорию можно снять. Пустое описание удаляет прежнее описание.
- Изменение состояния — отдельное действие, а не неявное последствие сохранения текстовых полей.
- Сохранение редактирования не меняет владельца, ID, время создания или состояние/время завершения.
- Completed-задачу разрешено редактировать.
- Отмена редактирования не отправляет сохранение. При ошибке введённые данные не теряются, пока пользователь остаётся на форме.
- После сохранения сохраняется текущий контекст списка. Задача может исчезнуть, если больше не подходит поиску/фильтрам; интерфейс сообщает об успешном сохранении.

## 5. Завершение и повторное открытие

- Active → Completed: устанавливается время завершения на сервере.
- Completed → Active: время завершения очищается.
- Повторное требование того же состояния успешно и не меняет первоначальное время завершения.
- Клиент отправляет желаемое состояние, а не команду «инвертировать»: повтор одного запроса не должен отменять его результат.
- Все остальные поля сохраняются.
- После подтверждения обновляется текущая страница и счётчик результатов. Изменённая задача может переместиться из-за сортировки либо исчезнуть из-за status-фильтра.

Следствие для раннего архитектурного эскиза: `TaskAlreadyCompletedException` не является обязательным требованием; повторный запрос Completed по этому контракту не бизнес-ошибка.

## 6. Удаление

- Перед удалением пользователь подтверждает действие; Active и Completed удаляются одинаково.
- Отмена подтверждения не изменяет данные.
- Удаление окончательное, без корзины и восстановления. Категория при удалении задачи сохраняется.
- Отсутствующая или чужая задача даёт один и тот же результат «Задача не найдена»; повторное удаление отсутствующей задачи тоже даёт этот результат.
- После успешного удаления обновляется текущий список и totalCount. Если страница оказалась за последней доступной страницей, открывается ближайшая существующая предыдущая страница; при нуле результатов — первая.

## 7. Минимальные категории

- Категория принадлежит одному пользователю и имеет серверный ID и название.
- Название обязательно: 1–50 Unicode code points после удаления whitespace по краям, без управляющих символов.
- Для одного пользователя названия уникальны без учёта регистра; внутренние пробелы не схлопываются. Разные пользователи могут иметь одинаковые названия.
- В MVP доступны создание и список своих категорий, упорядоченный по названию с устойчивым ID tie-breaker.
- Новая категория доступна для выбора в задаче после подтверждённого создания.
- Использование категории необязательно. Текст «Без категории» — UI-состояние, не специальная запись в БД.
- Переименование/удаление категорий и смена их владельца пока вне scope. Каскадного удаления задач по категориям не проектируем.
- Управление категориями — отдельный full-stack срез внутри эпика, не обязательная предпосылка первого среза создания задачи без категории.

## 8. Поиск и фильтрация

- Поиск — буквальное вхождение подстроки в **название** задачи без учёта регистра. Описание в MVP не участвует.
- Строка поиска обрезается по краям; whitespace-only означает отсутствие поиска. Максимум — 200 Unicode code points после обрезки; превышение даёт ошибку валидации.
- Нет fuzzy search, транслитерации, исправления опечаток или разбиения на слова. `%`, `_`, `[` и подобные знаки ищутся как обычные символы, а не шаблон запроса.
- Фильтр состояния: Все / Активные / Выполненные; по умолчанию Все.
- Фильтр категории: Все / Без категории / Одна выбранная категория; по умолчанию Все. Несколько категорий одновременно не выбираются.
- Поиск и фильтры применяются совместно по AND, до пагинации и расчёта totalCount.
- Поиск/фильтры не изменяют данные задач.
- Изменение поиска, фильтра либо размера страницы переводит пользователя на первую страницу.
- Если фильтр с корректным ID категории ничего не находит, в том числе для чужого/отсутствующего ID, возвращается пустая выборка, без раскрытия данных категории.

## 9. Порядок и пагинация

- Порядок фиксирован: Active перед Completed, внутри группы время создания по убыванию, затем ID по возрастанию для одинакового времени. Приоритет пока не влияет на сортировку.
- Нумерация страниц начинается с 1. Размеры страницы: 10, 20, 50; по умолчанию страница 1 и размер 20.
- API возвращает items, totalCount отфильтрованной выборки, page и pageSize. Число страниц UI может вычислить.
- Нулевые, отрицательные, нецелые или неподдерживаемые значения параметров дают ошибку валидации. Неизвестные значения состояния/приоритета также отклоняются, а не заменяются значением по умолчанию.
- Валидный номер страницы за пределами результатов возвращает пустой items и актуальный totalCount, без серверной ошибки.
- Текущие поиск/фильтры/page/pageSize представлены query-параметрами UI URL: обновление страницы и back/forward восстанавливают представление списка.
- Данные читаются с сервера постранично; загрузка всех задач для клиентской пагинации не соответствует требованию.
- Между разными запросами возможны изменения данных: не обещаем snapshot списка, стабильность offset-страниц при конкурентных вставках или автоматический live-update.

## 10. Доступ и защита данных

- Любые операции с задачами/категориями требуют действительной сессии.
- Владелец определяется сервером из проверенной идентичности; переданный клиентом owner/userId не может выбрать чужой список или изменить владельца.
- Изоляция распространяется на список, детали, поиск, totalCount, редактирование, состояние и удаление.
- Любое обращение к конкретной чужой задаче неотличимо от обращения к отсутствующей: 404.
- Назначение отсутствующей или чужой категории даёт одинаковую ошибку поля category, без деталей её существования/владельца. Изменения задачи при этом не сохраняются.
- Все изменяющие запросы используют уже реализованную серверную CSRF-проверку. UI guard улучшает навигацию, backend проверяет доступ независимо от него.
- Задачи и описания не помещаются в диагностические логи целиком; публичные ошибки не раскрывают SQL, stack trace или чужие данные.

## 11. Навигация, ожидание и ошибки

- `/tasks` — основной защищённый список. После успешного входа пользователь попадает туда, а не остаётся на временном account view.
- Открытие защищённой страницы гостем ведёт на `/login`. Проверка первоначальной сессии завершается до решения о guest/authenticated-навигации.
- После первого API 401 очищается устаревшая client identity и предлагается вход. Сетевой сбой или 500 не считается logout.
- Для списка различаются loading, ошибка загрузки с повтором, отсутствие любых задач и отсутствие совпадений по поиску/фильтрам.
- Формы показывают field errors рядом с полями. Повторная отправка блокируется, пока выполняется операция.
- Подтверждённый успех не показывается до ответа API. Неподтверждённый из-за сети результат не объявляется ни успехом, ни доказанным откатом.
- Изменяющие запросы автоматически не повторяются. При неоднозначном результате интерфейс предлагает обновить данные перед ручным повтором.
- Действия доступны с клавиатуры; у полей есть labels, у ошибок — связь с полем, фокус и сообщения результата управляются предсказуемо.

## 12. HTTP-семантика для последующего проектирования

Для первого среза создания и списка принят [HTTP-контракт](tasks-http-contract.md); он не подтверждает наличие реализации. Остальные URL/DTO согласовать перед соответствующими срезами. Общие ожидаемые результаты:

- Создание — 201, чтение/сохранение/установка состояния — 200, успешное удаление — 204.
- Некорректные поля/параметры и CSRF — 400, но CSRF сохраняет свой отдельный ProblemDetails code.
- Отсутствующая сессия — 401; отсутствующая/чужая конкретная задача — 404.
- Дубликат названия собственной категории — 409 с ошибкой поля name.
- Field errors используют существующий ValidationProblem-подход и имена полей HTTP-модели. Domain entities не становятся публичным DTO.
- Неожиданные технические ошибки остаются 500, без маскировки под ошибку пользователя.

## 13. Конкурентные изменения

Для MVP принимаем last-write-wins для редактируемых полей: отдельной проверки версии, 409 concurrency-conflict и истории пока нет. Изменение состояния остаётся отдельной операцией и не должно неявно происходить при сохранении текста. Если другая вкладка удалила задачу, следующая операция получает 404. Более сильные гарантии потребуют отдельного решения.

## 14. План full-stack срезов и приёмка

1. **Мои задачи:** защищённая страница, создание без категории, список с серверной пагинацией, defaults, loading/empty/errors. После обновления страницы задача сохраняется. Два пользователя не видят данные друг друга.
2. **Изменить задачу:** просмотр полного содержимого, редактирование и очистка optional-полей, показ server errors, сохранение/отмена.
3. **Управлять выполнением:** Completed/Active, completion time, повтор одинакового состояния без изменения результата, обновление списка.
4. **Удалить задачу:** подтверждение/отмена, окончательное удаление, корректная страница после удаления последнего элемента.
5. **Разложить по категориям:** создать/просмотреть свои категории, уникальность в рамках владельца, назначить/снять категорию, отклонить чужую ссылку.
6. **Найти нужное:** поиск по названию, status/category filters, совместная работа с пагинацией, URL-state и back/forward.

Каждый срез включает UI, API, Application/Domain по необходимости, хранение и проверки. Приёмка требует не только тестов отдельных слоёв, но и ручного браузерного сценария. Ключевые security-регрессии: отсутствие сессии/CSRF, чужой ID, чужая категория и отсутствие чужих данных в поиске/счётчиках.
