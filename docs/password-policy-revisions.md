# Ревизии правил пароля

## Текущий выбор

- `PasswordPolicyRevisions.V1`: 15–256 Unicode code points, не только whitespace.
- `AuthPasswordPolicies.Registration` явно выбирает V1.
- `PasswordPolicyRevisions.Supported` хранит все наборы, которые могли разрешить пароль существующего пользователя. Коллекция и объекты правил неизменяемы.
- `AuthPasswordPolicies.Login` строится из поддерживаемых наборов: самый низкий minimum, самый высокий maximum, запрет whitespace-only только если он есть во всех наборах.
- `PasswordPolicy.Validate(password, rules)` реализует проверки один раз. Пустой пароль всегда отклоняется. Пароль не обрезается и не нормализуется.

Пока есть только V1, набор проверок входа и регистрации одинаков. Это осознанный текущий контракт, а не зависимость Login от Register.

## Добавление ревизии

1. Не редактировать опубликованную V1. Создать V2 в `PasswordPolicyRevisions` с новыми правилами.
2. Добавить V2 в `Supported`, сохранив V1 и другие исторические наборы.
3. Явно переключить `Registration` на V2.
4. Проверить V1 regression-тестами, добавить тесты V2 и совместимости login со старыми и новыми допустимыми паролями.
5. Согласованно обновить Angular-валидацию, подсказки и HTTP-контракт. Backend не передаёт схему правил во frontend автоматически.

Например, V2 с максимумом 512 не должна заблокировать вход с паролем длиной 300; одновременно ужесточение минимума V2 до 20 не блокирует старый пароль V1 длиной 15. Уменьшение минимума или разрешение whitespace-only тоже учитываются при построении совместимых границ.

Login допускает более широкий набор комбинаций, чем отдельная ревизия. Это не даёт вход без совпадения хеша: набор правил только ограничивает ввод до дорогой проверки пароля.

## Ограничения

- Эта модель описывает только длину и whitespace. Для иных правил нужно явно дополнить модель и алгоритм совместимости; это не универсальный движок правил.
- Не удалять старую ревизию из Supported, пока не доказано, что соответствующие пароли больше не используются.
- Изменение общей реализации проверки может изменить старую ревизию даже при неизменных параметрах; поведение защищают regression-тесты.
- Версия политики не сохраняется в БД. Аудит или принудительная смена пароля потребуют отдельного проектирования.
- Ревизия правил не равна версии алгоритма хеширования. Автоматический rehash пока не реализован.

## Login Application

`LoginHandler` проверяет вход, создаёт Email через общий адаптер ошибок к Domain VO, читает пользователя и проверяет хеш. Для отсутствующего пользователя используется singleton `IDummyPasswordHash`, созданный Infrastructure с текущими параметрами Identity. Отсутствие пользователя и неверный пароль дают одну `InvalidCredentialsException`; технические ошибки и отмена не маскируются.

Обработчик возвращает только UserId/Email, без cookie и claims. Login endpoint, сессии, rate limiting и Angular login ещё не реализованы.
